lite-audio-pool v1.1.0 — torture bench vs Howler.js

What this measures: both libraries dispatch N rapid sprite plays against a real Web Audio backend. Same synthesized sprite content, same sample rate, same target destination. Numbers are the wall-clock time to schedule N plays plus the pace at which sounds are actually reaching the destination during the burst.

Framing: Howler.js is a general-purpose audio library — it handles decoding, HTML5 Audio fallback for legacy browsers, format detection across MP3/OGG/WAV/etc., spatial audio, and much more that this bench does not exercise. lite-audio-pool is scoped to one narrow slice: pre-wired sprite dispatch with voice stealing for real-time games. The numbers below reflect only that slice. Different tools, different scopes.

Reading the numbers: Dispatch time is the wall-clock JS time to enqueue N plays into the library. This is the metric a real-time game cares about (frame-budget cost of firing sound effects). It does not include the actual audio rendering, which the browser does off-thread. Dispatch rate is N ÷ dispatch time. Both libraries end up making similar Web Audio API calls under the hood — the difference between them is how much per-play JS work sits above those calls. Voice cap: Howler defaults to 100 concurrent, lite-audio-pool uses 32 here. In steal-saturation mode the pool must fade out an oldest voice on every call; that is the pool's more-expensive path and still where the interesting number sits.
